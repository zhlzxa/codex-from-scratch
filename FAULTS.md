# The fault catalogue

Every fault this project has to survive, numbered. The number is the spine of
the whole tutorial: it appears in the chapter that hits the fault, in the test
that pins it, and here.

```
grep -rn "F04_07" steps/          # find the code and the test
```

**Status:** ✅ covered · ⬜ upcoming — **every unit is now written; nothing is ⬜.**

**How it was found** — the column that matters most:

| | |
|---|---|
| 🔴 | **crash** — announced itself |
| 🟡 | **silent** — no error, wrong result. The largest single category (56 of 259). Only found by going looking |
| 🟢 | **boundary test** — deliberately fed something extreme |
| 🔵 | **long run** — only appears after ~30 turns |
| 🟠 | **observability** — spotted while reading a transcript or trace |
| 🟣 | **review** — someone read the code |

> Bypasses verified by running the command under a real bash and watching the

| ID | Fault | Found | Root cause and fix |
|---|---|---|---|
| ✅ F05-01 | `git status; rm -rf /` defeats prefix matching | 🟢 → 🟡 | Segmenting on `;` `\|` `&` `&&` handles the listed case and **three others it does not**: a newline (`shlex` eats it as whitespace, bash runs the second line), a backtick glued into a word (`echo \`rm -f x\``), and an in-word `#` (`echo a#b; rm -f x` tokenises to `['echo', 'a']`). All three deleted a real file. `shlex` is a tokeniser, not a shell parser, and **every disagreement found was in the dangerous direction**. Patching them one at a time bets the list is now complete, so the question was inverted: `_MODELLED` is an allowlist of characters this code implements the meaning of; anything else makes the command unknown, and unknown asks |
| ✅ F05-02 | `git` allowed wholesale, including `push --force` | 🟢 | Subcommand granularity — plus the global options that come *before* it: `git -C /elsewhere status` reads another repository, `git -c core.pager='rm -rf /' log` runs a command. Remote subcommands are classified NETWORK, not "local write": the damage is on a server and is not undone by editing a file back |
| ✅ F05-03 | `../../` and symlinks defeat string comparison | 🟢 | **Already fixed in chapter 4** (F04-12, `paths.resolve()`); this chapter only added the test that says so. The real hole here was next to it and found by mutation testing: the `workspace-write` decision for shell commands — the core decision of the whole mode — had no test at all |
| ✅ F05-04 | `python -c "open('x','w')"` writes in read-only mode | 🟢 | Tokenising is *perfect* here and tells you nothing — the danger is inside a string argument. Interpreters (`python`, `node`, `sh`, `perl`, …) are classified INTERPRETER unconditionally, without looking at what they were handed |
| ✅ F05-05 | `curl` exfiltrates; `pip install` pulls a malicious package | 🟢 | Classified NETWORK, **recognised rather than blocked** — `pip` regardless of subcommand, since `pip download` fetches and `pip install` fetches *and executes* setup code. | ✅ F05-06 | Approval fatigue; user says yes to everything | 🔵 | Measured at 2–4 prompts per task on real runs. Remembered rules, each carrying scope, source and timestamp. **The first version of the rule checker refused `pytest`** — it rejected every one-word rule unless the program was read-only, which was tidier and wrong: the mechanism built to end approval fatigue could not be applied to the command that causes it. ## Chapter 8 · Concurrent tools ✅

> `probe_scheduler.py`, 30 trials per configuration, 2026-08-11.
> **The scheduler is list scheduling by declared resource, not locks**: each
> call's `Footprint` (what it reads, what it writes, or `STATEFUL` if neither
> question can be answered) decides which batch it lands in, and batch N+1
> never starts until batch N's `asyncio.gather()` has returned. Two of the
> nine listed faults did not reproduce the way they were written down — one
> because it turned out to already be impossible, one because the "slow
> machine" framing was backwards.

| ID | Fault | Found | Root cause and fix |
|---|---|---|---|
| ✅ F08-01 | Two patches to one file; last write wins | 🟡 | **Reproduced 30/30 — and 30/30 even with the artificial delay set to zero.** Two `apply_edits()` calls racing on one file both read the pre-edit content, both compute their own change correctly, both report `Applied 1 edit(s)` — and whichever writes second erases the other's change with no error anywhere. `footprint_of()` names every path an `apply_patch` call touches; `conflicts()` treats write/write on the same path as a conflict; `batches()` puts the two calls in different batches, so the second `read_source()` cannot run until the first `write_source()` has returned |
| ✅ F08-02 | Read overlaps a write; model sees half a file | 🟢 | Same resource key, different verb: `conflicts()` treats a write touching what a read touches (either order) as a conflict too, not only write/write. Measured with a peak-concurrency tracker around `_read()` and `write_source()`: with the scheduler wired in, the two never overlap (peak 1 across every run); the interesting number would be what an *unscheduled* `asyncio.gather()` does, and that is exactly F08-01's mechanism read the other way round — no separate reproduction needed |
| ✅ F08-03 | Stateful commands run concurrently | 🟢 | `run_shell` classifies `STATEFUL` unconditionally — not "detect that this particular command uses `cd`", which is the same shape of mistake F05-01 made about shell syntax (guessing at meaning instead of refusing to guess). | ✅ F08-04 | One raises, siblings' results lost, orphan calls | 🟣 | **Does not reproduce, and cannot with this codebase**: `_run_tool()` has turned every ordinary exception into a returned string since chapter 0 (F00-05), so the coroutine `asyncio.gather()` awaits here never raises `Exception` for a failing tool — gather's fail-fast/cancel-siblings behaviour only triggers on a raised exception, and an ordinary tool failure was never going to produce one. | ✅ F08-05 | Completion order ≠ call order | 🟡 | Matching by `call_id` (chapter 1, F01-03) already made this safe for the API. | ✅ F08-08 | Cancellation does not reach every task | 🔴 | Generalises chapter 7's F07-04 rule (every issued call is answered, including ones that never started) from "one call at a time" to "one batch at a time, plus every batch after it." `asyncio.gather()` already cancels every task it is still awaiting when the await on `gather()` itself is cancelled; the part that is not automatic is reading `.cancelled()` / `.result()` afterwards without racing that cancellation, which is what the follow-up `asyncio.gather(*tasks, return_exceptions=True)` is for. | ✅ F08-09 | Only reproduces on slow machines | 🟠 | **Backwards, at least for F08-01 on this machine**: the write/write race reproduced 30/30 with the artificial delay removed entirely (0.000s, 0.001s, 0.050s — all 30/30). | ✅ F12-01 | 400s retried forever | 🔴 → 🟡 | **The status code cannot decide this and neither can `type`.** `context_length_exceeded` and "your tool name has a space in it" are both HTTP 400 with `type: invalid_request_error`, and they are the two extremes of the table. ## Chapter 20 · The sandbox: permission was a judgement, not a boundary ✅

> Chapter 5 built the judgement layer and wrote down, in its own fault list,
> the two things it could not do: **F05-04** (`python -c "open('x','w')"`
> writes in `read-only`, because "tokenising is *perfect* here and tells you
> nothing") and **F05-05** (`curl` exfiltrates, "recognised rather than
> blocked … a real network policy needs the OS sandbox this chapter does not
> build"). This chapter builds it, on Linux, with bubblewrap — and both
> payloads stop, measured: `OSError: [Errno 30] Read-only file system` and
> `curl exit=6`.
>
> **The return was not only safety.** `_SHELL_ALLOWED_BY_MODE` grants
> `workspace-write` exactly `{READ}` — writing asks even in the mode named for
> writing, because *where* the bytes landed was unknowable. Under a boundary
> the kernel answers that, so a confined session may write without asking, and
> the prompts removed are precisely the ones F05-06 measured a user learning
> to click through unread.
>
> **Two faults were found by measurement rather than by the list**, and both
> changed the design. Binding only the workspace is not a tighter sandbox but
> a broken one (`bwrap: execvp /bin/sh: No such file or directory` — the
> interpreter has to be reachable), so the shape is bind `/` read-only and
> punch writable holes. And bwrap's own setup failures exit **1**, the same
> code as a command that ran and returned 1, so the exit code cannot tell a
> containment failure from a business error — which is F05-09's shape arriving
> through a new door.
>
> **The chapter's own verification failed first.** Two of 25 mutations
> survived, both in `shell.py`'s seam, because every test that would have
> caught them needed a real `bwrap` and was skipped on the development
> machine. That is chapter 19's fault repeating one chapter later, and the
> repair is narrower than chapter 19's: *the wiring is not the mechanism*.

## Chapter 22 · Connecting a server from the console ✅

> Chapter 21 gave the library remote MCP and OAuth. The console could not
> reach any of it: its add-server form asked for a command and nothing else,
> and `runtime.py` turned every stored record into a `ServerConfig` without
> ever asking what shape it was. So the answer to "can a user of the web
> console connect to GitHub" was no, and had been since the moment chapter 21
> merged -- a capability that exists in a library nobody can call from the one
> interface most people will actually use is not a shipped capability.
>
> **The interesting part is not the form.** Chapter 21's OAuth is written for a
> terminal: `redirect_handler` opens a browser on this machine, and
> `callback_handler` binds a loopback socket and blocks until the redirect
> arrives on it. Both assume the process asking for authorization and the
> browser granting it share a machine. A console serving a browser somewhere
> else breaks that assumption in both directions -- the server cannot open
> anybody's browser, and a remote browser cannot reach the server's loopback
> port. One blocking call has to become two HTTP requests with a person in
> between, and everything the first one learned has to survive until the second
> one arrives (F22-01).
>
> **No codex comparison exists for most of this chapter.** codex is a CLI and a
> TUI; it has no web console, so it has no browser-mediated OAuth, no pending
> attempt table and no server-rendered callback page. The parts that *do* trace
> to codex -- the remote server config's shape, the preset `client_id` posture
> -- are chapter 21's citations, still good, and reused rather than restated.
> Where this project goes past codex, the honest sentence is "codex does not do
> this", not a strained analogy to something in `codex-rs` that is not the same
> thing.

| ID | Fault | Found | Root cause and fix |
|---|---|---|---|
| ✅ F22-01 | **Chapter 21's OAuth handlers assume the browser is on the machine running the agent.** A server-hosted console breaks that in both directions: it cannot open a browser for a person who is somewhere else, and that person's browser cannot reach a loopback port on the server | ⚫ | The one blocking `async_auth_flow` call is split into two of this console's own routes with a browser round trip between them. `POST /api/mcp/oauth/start` does everything the SDK would do before it needs a human -- protected-resource discovery, authorization-server discovery, registration or a preset client, PKCE -- and returns the authorization URL instead of opening it; `GET /api/mcp/oauth/callback` is where the redirect actually lands, arbitrarily later. None of RFC 7591, 8414 or 7636 is reimplemented: `web/oauth.py` drives the SDK's own `OAuthContext`, `PKCEParameters` and discovery helpers directly, because only the *seam* is new. The same fact decides what a turn does with an unconnected server: `resolve_mcp_configs` refuses it by name with a `needs_connection` status, because the only callbacks a turn could pass are the two that raise -- a process with no browser must not pretend it can show one |
| ✅ F22-02 | **The callback route's only input is a query string the browser carried back**, and a `state` a stranger can guess or replay is an open door: it decides which pending attempt -- and therefore which server's credential -- a code is exchanged for | 🟣 | `state` is generated server-side by `secrets.token_urlsafe` and is only ever *looked up*, never believed: `PendingOAuthTable.pop` returns `None` for an unknown, expired or absent value, and every request that misses gets the identical answer, so the route says nothing about which states exist. Nothing downstream of that lookup reads the query string for *which server this is* -- that comes from the pending entry, which the server wrote |
| ✅ F22-03 | **An attempt that is started and never finished never goes away.** Somebody clicks Connect, thinks better of it, and closes the tab; the entry -- with its code verifier and discovered endpoints -- sits in the table until the process restarts | 🔵 | A ten-minute TTL, swept lazily on the next `put`/`pop` rather than by a background task: one fewer thing running when nothing is happening, at the cost of holding one expired entry between sweeps. | ✅ F22-04 | **`add_mcp` accepted a record that was neither shape, or both.** A server with a `command` *and* a `url`, or with neither, was stored happily and only became a problem at connect time, one turn later and one layer away from the form that produced it | 🟢 | Refused at the door with a message about the form the person is looking at. `mcp.load_config` already applies the same rule to a config *file* (F21-01), and it is applied twice on purpose: the library's job is to raise for its caller, the route's job is to tell a human which field to fix. The same duplication covers the authentication pair -- a bearer token and OAuth on one server is refused by the route, and refused again in `server_config` for a record that reached storage some other way, such as a hand-edited `mcp.json` |

**F22-05 was on the plan and is not on this list.** It was a guess -- that
`mcp_status` might need to distinguish "configured but never connected" from
"connected but never used" -- and building the chapter answered it: the first
half is F22-01's `needs_connection` status, which falls out of the
architecture rather than being a separate finding, and the second half is a
usage question no measurement in this chapter asked. A planned fault number
that the work does not justify is dropped, not padded into existence.

Design decisions this chapter made and did not turn into faults, because
nothing was ever broken by them:

| Decision | Why |
|---|---|
| **The console polls `GET /api/mcp/{id}/oauth/status` instead of a `postMessage` handshake.** | `window.open(url, "_blank", "noopener")` is what the browser actually calls, and `noopener` is the reason a handshake is not an option: the new tab has no reference back to message. Choosing `postMessage` would have meant choosing a mechanism that only works if a *less safe* call is made. Deliberately not built, and stated rather than left to be discovered: **the
console is still single-tenant.** Its OAuth tokens are stored under

one occupant of it. Authentication, sessions and quotas for this project's own
multi-user deployment are chapter 23's, and until they exist "who is this
browser" has exactly one answer.

And the honest state of GitHub, which is what this chapter was asked for: a
**personal access token works today** -- paste it into the remote form, no
flow, no browser, nothing to register. **Interactive OAuth against GitHub
additionally requires whoever runs the console to register a GitHub OAuth App
first** and put its client id in the form, because GitHub's authorization
server advertises no `registration_endpoint` (measured in chapter 21, F21-08b)
and so the SDK's dynamic registration has nothing to call. The button does not
remove that step; it makes every step after it a click.

## Chapter 23 · Who is using this console ✅

> Chapter 20 built `tenancy.Owner` and wrote down, in the module's own
> docstring, exactly what it was not: "this is the *seam*, not a multi-user
> system. There is no registration here, no session, no password, no quota, and
> `Owner.key` is trusted completely by whoever constructs it. A server that
> derives an owner from an unauthenticated request header has moved the leak,
> not closed it." Three chapters later nothing constructed one but
> `DEFAULT_OWNER`, and `serve()`'s own docstring said the rest out loud: this
> process "runs shell commands and edits files on behalf of whoever can reach
> it, with an approval prompt as the only gate, and it has no authentication of
> any kind."
>
> **The chapter's one idea is that multi-tenancy is mostly not a permission
> check.** A check is a line somebody has to remember to write, on every route,
> forever; the failure mode of forgetting is silence. So the three tables that
> made a check necessary stop being one table: the record store is one per
> owner, the approval broker is one per account, and the event channel's keys
> carry the account. After that, "is this thread bob's" is not a comparison
> anybody can skip -- alice's thread is not *forbidden* to bob, it is not in the
> store his request was handed. The same argument runs one level up: the
> authentication gate is a middleware that refuses everything under `/api` and
> `/ws` with a three-line exception list, rather than a `Depends(...)` a new
> route can be written without.
>
> Where a shared table is genuinely unavoidable -- the session list, which has
> to be one table so that "sign out everywhere" can exist -- the lookup takes
> the account *and* the id as a pair, and a mismatch is simply not found.
>
> **The mechanism is not codex's, and there is no pretending otherwise.** codex
> is a CLI and a TUI; it authenticates *to* ChatGPT and never *for* anybody, so
> it has no login, no session, no account list and no quota. This chapter is
> the second half of this project going past its prototype, and the sentence
> worth repeating from chapter 22 applies again: "codex does not do this" is
> more useful than a strained analogy to a file in `codex-rs` that is not the
> same thing.

Design decisions this chapter made and did not turn into faults, because
nothing was ever broken by them:

| Decision | Why |
|---|---|
| **Local accounts and a password, not "sign in with GitHub".** | OAuth 2.0 is an *authorization* protocol: a completed flow yields a token that acts on a resource, and "the holder of this token can read a GitHub repository" is not the proposition "the person in this browser is `alice`". Treating one as the other is a documented class of bug. The second reason is decisive on its own: chapter 22 measured that GitHub publishes no `registration_endpoint` (F21-08b), so a GitHub login would require whoever runs this console to register an OAuth App *before the first person can sign in at all*, and a self-hosted tool that cannot be started without paperwork on somebody else's website is not self-hosted |
| **`hashlib.scrypt`, and no cryptography of this project's own.** | "Hand-roll what you are teaching, depend on what you are not" -- password hashing is not what this chapter teaches and is the worst candidate in the program for a from-scratch implementation. RFC 7914 is in the standard library, so there is no dependency to add either. What the code does choose is the cost (2\*\*14, the interactive figure from RFC 7914 §2, ~150 ms and 16 MiB per verification) and a self-describing encoding, `scrypt$n$r$p$salt$key`, so raising the cost later leaves every existing password verifiable |
| **A one-time bootstrap token printed to the terminal, held only in memory.** | The alternatives are worse in ways worth naming. A default password is a published credential on every install that skipped the second step. An unauthenticated "create the first account" route is the same thing without the password: whoever reaches the port first becomes the operator. A token printed to the terminal that started the process binds the first account to whoever could read that terminal, which is the person who decided to start the server. Jupyter reached this conclusion first; the reasoning is general |
| **Sessions live in the process and are not persisted.** | A restart signs everybody out, which is the behaviour of a tool you start rather than a limitation of it. A `sessions.json` would buy convenience and cost a second credential file on disk written on almost every request (the idle clock moves when a request arrives), and it would outlive what it refers to -- a session that survives a restart points at approvals that no longer exist and turns that are no longer running. The token is still stored *hashed* in that in-memory table, because `GET /api/auth/sessions` renders it and a table of raw tokens is one careless serialisation away from handing out live credentials |
| **`Secure` on the session cookie only when the request was https.** | Set unconditionally it is discarded by the browser on plain `http://localhost:8000`, which is how this console is normally run, and logging in would appear to succeed and then not work. `HttpOnly` and `SameSite=Lax` are unconditional; `Lax` is this console's CSRF defence, and it is sufficient while every state-changing route is a POST, PATCH or DELETE |
| **Pre-chapter-23 records are adopted by the first account, once, at bootstrap.** | Four chapters of consoles wrote `threads.json` and its friends into the top of the data directory. Leaving them means the operator's first sign-in shows an empty console with all their sessions on disk one level up, which reads as data loss whether or not it is. Once, from the bootstrap route, and never on start -- a console that adopts stray files whenever it finds them would hand the *next* account whatever the previous one left behind. It is a rename that stops at the first target which already exists, because nothing here knows how to reconcile two `threads.json` files and pretending otherwise is how one of them is lost quietly |
| **Disable, never delete an account.** | An account key is a directory name under two different trees, one of which holds OAuth tokens for other people's servers. Removing the row while the directories stand would let the same key be handed out again and inherit them. A disabled account cannot sign in, its live sessions are revoked, and what it owns stays where it is until somebody decides on purpose what to do with it |

One mutation in this chapter is an equivalent mutant and is caught by a
*static* assertion rather than a behavioural one, which is worth stating
plainly rather than hiding in a green tick. `hmac.compare_digest(a, b)` and
`a == b` return the same value for every input; no behavioural test can tell
them apart, and timing a 32-byte comparison inside CPython measures the
interpreter. The property is real and is a property of the text, so
`test_the_password_comparison_is_constant_time` reads the line -- the same
shape chapter 19 uses for a frontend confirmation dialog (F19-11), with the
same limit, which is that a static assertion can tell you a function was
called and not that it does what its name says.

Reproduce these counts with:

```
grep -cE '^\| (✅|⬜|—) ' FAULTS.md          # 259 entries
grep -cE '^\| (✅|⬜|—) .*🔴' FAULTS.md      # 24 crashes
```

Only 24 of 259 announce themselves. The other 235 — 91% — produce no
exception at the moment they happen: a wrong answer, a slow answer, a worse
answer, or nothing at all until a user complains.

That ratio is the argument for everything in chapter -1. You cannot wait for
these to report themselves. You have to go looking, and going looking requires
tooling you built before you needed it.
